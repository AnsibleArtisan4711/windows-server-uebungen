> [!WARNING]
> **Stand der Prüfung: Entwurf, nicht im Labor ausgeführt.** Anforderungen an das Zertifikat (Server Authentication, vertrauenswürdige Ausstellung, exportierbarer Schlüssel, `.pfx`), der Weg über *Edit Deployment Properties → Certificates* und `Set-RDCertificate`/`Get-RDCertificate` stammen aus Microsoft Learn (12.11.2026). **Nicht bestätigt:** `New-RDCertificate` (Parameter), die Rollennamen für Broker, das Erscheinungsbild der Warnung nach dem Import auf dem Client und der Zeitpunkt, ab dem die Warnung entfällt.

## Lernziele

Nach dieser Übung kannst du

- die Zertifikatsanforderungen der RDS-Rollen erklären
- Zertifikate für Broker und Web Access in der Bereitstellung erzeugen und zuweisen
- dem Client das Vertrauen herstellen und die Wirkung prüfen

## Voraussetzungen

- Modul 05 abgeschlossen.
- Es gibt im Labor keine Zertifizierungsstelle. Du arbeitest mit selbst signierten Zertifikaten; der Kurs „Zertifikatsdienste und PKI (AD CS)“ zeigt den Weg über eine eigene CA.

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| EKU Server Authentication | Erweiterte Schlüsselverwendung 1.3.6.1.5.5.7.3.1, für Server erforderlich. |
| .pfx | Datei mit Zertifikat und privatem Schlüssel, durch Kennwort geschützt. |
| Vertrauenswürdiger Stamm | Speicher `Cert:\LocalMachine\Root`, aus dem Clients Aussteller als vertrauenswürdig akzeptieren. |

## Testumgebung

| Gerät | Rolle in Modul 06 |
|---|---|
| RDS01 | Zertifikate erzeugen und zuweisen |
| CL01 | Vertrauen herstellen, Test |

## Aufgabe

### Teil 1: Anforderungen

*(Lerneinheit 6.1, Praxisaufgabe 1)*

Notiere die Anforderungen laut Microsoft Learn (Server Authentication, vertrauenswürdige Aussteller, exportierbarer privater Schlüssel, `.pfx`-Export) und die Namen der Rollen: `rds.rdslab.internal` für Web Access, `rds01.rdslab.internal` für den Broker.

### Teil 2: Erzeugen und zuweisen

*(Lerneinheit 6.2, Praxisaufgabe 2)*

Menüweg (Microsoft Learn): *Server Manager → Remote Desktop Services → Overview → Tasks → Edit Deployment Properties → Certificates*. Lege über *Create new certificate* selbst signierte Zertifikate an für

- **RD Connection Broker – Enable Single Sign On** (Name `rds01.rdslab.internal`),
- **RD Connection Broker – Publishing** (Name `rds01.rdslab.internal`),
- **RD Web Access** (Name `rds.rdslab.internal`).

Speichere die `.pfx`-Dateien mit *Store this certificate* in einem Ordner auf `RDS01` (zum Beispiel `C:\Certs`). Das Kennwort tippst du interaktiv ein. Aktiviere *Allow the certificate to be added to the Trusted Root Certification Authorities certificate store on the destination computers*, dann *Apply*.

Prüfen:

```powershell
Get-RDCertificate -ConnectionBroker 'rds01.rdslab.internal'
```

Die Ausgabe zeigt je Rolle Subjekt, Gültigkeit und Stand (*sinngemäß*). Alternativ lässt sich ein vorhandenes `.pfx` per PowerShell zuweisen (Syntax aus Microsoft Learn):

```powershell
$password = Read-Host -AsSecureString -Prompt 'Kennwort der PFX-Datei'
Set-RDCertificate -Role RDWebAccess -Password $password -ImportPath 'C:\Certs\rdweb.pfx' -ConnectionBroker 'rds01.rdslab.internal'
```

### Teil 3: Vertrauen auf dem Client

*(Lerneinheit 6.3, Praxisaufgabe 3)*

Exportiere die öffentlichen Zertifikate ohne privaten Schlüssel (`certlm.msc` auf `RDS01` → Persönlich → Zertifikate → Rechtsklick → *All Tasks → Export*, *No, do not export the private key*) und kopiere die `.cer`-Dateien nach `CL01`, zum Beispiel über die Admin-Freigabe `\\rds01.rdslab.internal\c$\Certs`. Auf `CL01` als Administrator:

```powershell
Import-Certificate -FilePath 'C:\Temp\rdweb.cer' -CertStoreLocation 'Cert:\LocalMachine\Root'
```

Rufe `https://rds.rdslab.internal/RDWeb` neu auf (Browser neu starten). Erwartet: keine Zertifikatswarnung; Abweichungen notierst du.

### Teil 4: Prüfpunkt

*(Praxisaufgabe 4)*

```powershell
foreach ($vm in 'DC01','RDS01','CL01') { Checkpoint-VM -Name $vm -SnapshotName 'M6-Zert' }
```

## Hinweise

- Die `.pfx`-Dateien enthalten private Schlüssel. Sie gehören nicht in ein Repository und nicht in einen Bericht. Das Kennwort steht nicht im Text.
- Exportiere für den Client nur die öffentlichen `.cer`-Dateien.
- Importiere im Labor nur diese Laborzertifikate in den Stammspeicher von `CL01` und entferne sie nach dem Kurs wieder.

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Zielzustand**

- Zertifikate für Broker (SSO und Publishing) und Web Access zugewiesen, `Get-RDCertificate` zeigt sie, `CL01` vertraut ihnen, `https://rds.rdslab.internal/RDWeb` ohne Warnung (oder Abweichung notiert), Prüfpunkt `M6-Zert`.

**Antworten**

1. Der Client vergleicht den aufgerufenen Namen mit dem Namen im Zertifikat. Weicht er ab, kann ein Dritter sich als Server ausgeben; deshalb warnt der Browser.
2. Broker (Single Sign-On und Publishing), Web Access und Gateway (Modul 07). Hier: Broker und Web Access.
3. Jeder Client muss dem Aussteller einzeln vertrauen, es gibt keine zentrale Sperrung, und der Schlüssel liegt auf dem Server. Eine CA mit Verteilung per Gruppenrichtlinie löst das (anderer Kurs).


</details>
